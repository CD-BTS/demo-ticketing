# Issue #18 실행 기록 — 자원 부족으로 예비 단계 중단

브랜치: `test/#18/redis-queue-performance`. 실행 시각: 2026-11-07 23:42 한국시간.

## 결론

**1 VU A 환경의 서버 시작 단계에서 보호 중단했다. k6는 시작하지 않았다.** 따라서 A/B 예비 검증, 10/50/100 VU 비교, 세 번 반복 및 성능 효과 분석은 완료하지 않았다. 200/500 VU·도착률·TTL 실험은 실행하지 않았다.

운영 로직·DB 스키마·프론트엔드는 수정하지 않았다. 생성한 전용 Java 프로세스와 MySQL·Redis 컨테이너는 정리했으며 기존 Demo MySQL·Redis는 유지했다. 다른 애플리케이션은 종료하지 않았다.

첫 명령은 BUILD SUCCESSFUL이며 성능 전용 Java 클래스가 실제 컴파일되었다. 두 번째 명령은 가용 RAM 보호 조건으로 종료 코드 1이다. 부하 테스트 성공이 아니다.

중단 후 실행기에는 가용 RAM **2GiB** 사전 점검을 추가했다. 이후 이 조건을 충족하지 않으면 Gradle 빌드·컨테이너 생성도 시작하지 않는다. 이 추가 안전 경로는 구문 검증했으며, 서버 부하를 재시도하지 않았다.

## 실제 자원 표본

호스트는 논리 CPU 8개, 가시 물리 RAM 8276901888 bytes(약 7.71GiB)다.
전용 MySQL·Redis 시작 후 Java 초기화 단계에서 다음 3개 표본을 수집했다.

| 시각 UTC | 가용 RAM MiB | Pages Input/sec | Java CPU % | Java RSS MiB |
|---|---:|---:|---:|---:|
| 14:42:37.446 | 421.17 | 1221.25 | 최초 표본이라 미수집 | 52.02 |
| 14:42:38.458 | 439.54 | 4858.56 | 22.51 | 93.86 |
| 14:42:39.474 | 362.80 | 4597.80 | 36.33 | 126.86 |

Java CPU는 논리 CPU 8개 전체를 100%로 정규화했다. 이 값은 서버 시작 시 CPU이며 API 부하 시 CPU가 아니다.
가용 RAM 768MiB 미만이 3회 연속 관측되어 중단했다. 실제 OOM 발생까지 밀어붙이지 않았다.
Pages Input/sec에는 파일 페이지 읽기가 포함되므로 전부 스왑이라고 단정하지 않는다. 보호 중단 이유는 가용 RAM 부족이다.

정리 후 읽기 전용 점검에서도 가용 RAM은 약 929MiB였다. 이 상태에서 10/50/100 VU로 확대하면 공정한 서버 비교보다 호스트 메모리 경합을 측정할 가능성이 높다.
